## What this changes and why

Tomáš wants the campaign to deliver a **"finish the game in an hour"** experience (already
the target in `GAME_DESIGN.md` §13) with the difficulty **evenly spread**, and — this is
the new part — an explicit, felt progression from *"early missions: enemies patiently
drift in and wait to be destroyed"* to *"late missions: enemies fly at you and kill you."*

I pulled real data before writing this, not assumptions:

1. **The passive→aggressive curve already exists mechanically, but unevenly and
   un-formalized** — every enemy kind already has a `speed` stat, and kinds are already
   introduced roughly in speed order across the mission list. But it's an accident of
   authoring order, not a stated design rule, and one mission (m5) breaks the pattern
   badly (see below).
2. **I ran a fresh balance sweep today** (`pnpm balance`, 36 combos × 500 runs = 18,000
   sims) and it reproduces exactly the balance debt already on record from 2026-06-20 —
   nothing has drifted, this is a stable, known problem, not a regression:

   | Mission | Clear % (starter/greedy) | Target band | Status |
   |---------|--------------------------|--------------|--------|
   | m1 First Contact | 58.8% | 70–90% | ⚠️ too hard |
   | m2 Picket Line | 83.6% | 70–90% | ✓ |
   | m3 The Wall | 49.4% | 70–90% | ⚠️ too hard |
   | m4 Blockade | 77.4% | 70–90% | ✓ |
   | m5 Asteroid Run | **10.6%** | 70–90% | ❌ near-impossible on starter/mid gear |
   | m6 Leviathan | 74.4% | 70–90% | ✓ |

   Full breakdown in `v2/tools/balance-report.md` (regenerated by this session; also
   flags several **unreachable stars** (all under the tool's 5% threshold) — e.g.
   `m1-time-t4` at 0.2%, `m3-hull-90` at 0.4%, `m3-shield` at 0%, `m5-hull-90` at 0%,
   `m5-all-kills` at 4.4%, `m5-shield` at 0% — meaning the time-star thresholds were
   likely hand-picked rather than calibrated from real run data).
3. m5's near-total failure on starter/mid gear (10.6%/24%, jumping to 85% only at
   "full" loadout) lines up with a **structural pacing problem**, not just "numbers are
   off": m5 is the *only* main mission with **zero patient-tier breathing room** — it
   opens directly into a swarm flood (speed 2.4, ~4.2s time-to-impact) with no earlier
   slow-enemy warm-up, unlike every other mission. That's a concrete, testable hypothesis
   for *why* it's broken this way — see item 1.

This document proposes: (1) a named, explicit aggression-tier model to structure mission
design going forward; (2) how that reframes the m5 problem specifically; (3) fixing the
mechanical process gap that's produced unreachable stars; (4) a two-layer testing
approach (simulator + manual playtest) so pacing and *feel* are both checked, not just
clear-rate — the previous polish pass on this project found real bugs (missing skip
button, silent rear weapon, blank state colors) that the simulator structurally cannot
see, because it never renders anything.

## Item 1 — Formalize the aggression-tier model

### The mechanic already in the code

`enemy.distance -= enemy.speed` every tick (`v2/src/core/conveyor.ts:16`), 10 ticks/sec,
lane length 100 (`v2/src/core/constants.ts`). So **time-to-impact from spawn** ≈
`10 / speed` seconds — a clean, already-computable number per enemy kind:

| Kind | `speed` | Time-to-impact | Read as |
|------|---------|-----------------|---------|
| turret | 0 | never advances | stationary — a DPS check, not a threat that "arrives" |
| boss | 0.25 | ~40s | slow, inevitable, blocks the timeline |
| blocker | 0.5 | ~20s | slow, blocks the timeline until killed |
| tank | 0.6 | ~17s | slow, high-HP DPS sponge |
| guardian (t1 slow) | 0.15 | ~67s | deliberately near-stationary — the tutorial's whole point |
| fodder | 1.2 | ~8.3s | baseline — comfortably shootable |
| striker | 1.6 | ~6.3s | faster, higher damage, starts to pressure |
| swarm | 2.4 | ~4.2s | fast, low HP individually, dangerous in volume |
| kamikaze | 2.8 | ~3.6s | fastest — "primary threat is collision, not shots" (`GAME_DESIGN.md` §8) |

### Proposed three-tier model

| Tier | Kinds | Time-to-impact | Player experience |
|------|-------|-----------------|---------------------|
| **Patient** | fodder, tank, blocker, turret, boss | ≥ 8s (or stationary) | "it's drifting in, I have time to shoot it down" |
| **Escalating** | striker (6.3s), swarm (4.2s) | 4s – <8s | "I need to actually manage energy/fire rate now" |
| **Aggressive** | kamikaze | < 4s | "it's coming to kill me, collision is the real threat" |

(Bands are 4s/8s cutoffs, not 4-6s — striker's 6.3s sits inside Escalating, not in a gap
between two disjoint bands. Fixed after Fable's review flagged the original 4–6s /
≥8s framing as leaving striker uncovered.)

Mapped against the *current* mission list, this is already mostly true:

- **m1, m2** (Patient-dominant, light Escalating in the final push) — matches today's
  design already: m1 is fodder→striker, m2 is fodder/striker alternating→tank finale.
- **m3, m4** (Escalating-with-Patient-carryover) — m3 stays fodder/tank/blocker
  (all-Patient, surprisingly — it never actually introduces striker/swarm!); m4 is
  striker-heavy with blocker gates.
- **m5** (should be Escalating-dominant with an Aggressive-tier finale) — **is currently
  100% swarm from second 2, with zero Patient-tier warm-up**, then jumps straight to a
  blocker finale (Patient-tier, oddly — a slow enemy as the "hard part" of the hardest
  mission is backwards from the model).
- **m6** (full mix, Aggressive tier introduced) — already matches: fodder→striker→swarm→
  tank→**kamikaze**→boss, the one mission that actually reaches the Aggressive tier.

**This reframes m5's balance problem as a design-shape problem, not (only) a numbers
problem**: m3 never leaves the Patient tier at all (arguably too gentle for mission 3 of
6), while m5 skips Patient entirely (too harsh for mission 5 of 6, and the numbers make
it worse). A more even spread would look like: m1–m2 mostly Patient, m3 introduces
Escalating properly (currently missing), m4–m5 Escalating-dominant, m6 the only one
reaching Aggressive. **This is a design-shape opinion, not a stat change — it's safe for
this document to propose; it's not safe for this document to also decide the exact
enemy counts/spacing that realize it.**

### Design decisions requiring confirmation
- Is the 3-tier framing (Patient / Escalating / Aggressive) the right mental model, or
  does Tomáš think in different terms? **No default recommendation given here** — this
  is a creative call, not a mechanical one.
- Should m3 be re-shaped to introduce Escalating-tier enemies (striker/swarm) rather than
  staying all-Patient? If yes, that's a real content change to `missions.ts`, subject to
  the same "Tomáš approves the specific numbers" rule as m5.
- Should m5 gain an explicit Patient-tier opening (e.g. a short fodder wave before the
  swarm ramp) as the fix, or is the real fix a numbers-only change (fewer/weaker swarm
  enemies, unchanged shape)? Both are plausible; only Tomáš should pick.

## Item 2 — "Finish in an hour, evenly spread": reconciling target vs. measured time

`GAME_DESIGN.md` §13 gives a target combat-time table (m1+m2 ≈ 8 min, m3+m4 ≈ 14 min,
m5+m6 ≈ 25 min — a deliberately *uneven*, escalating split, not equal time per mission).
Today's fresh sweep's `avg-duration` column doesn't cleanly compare against that table,
for a specific reason worth flagging: **on missions with low clear-rate, `avg-duration`
is dragged down by fast failures**, not real full clears. m5 starter/greedy shows
"81.5s avg-duration" at only 10.6% clear — that number is mostly *defeat* time, not
completion time, so it can't be read as "m5 takes 81s." The same distortion, to a lesser
degree, likely affects m1 and m3.

**Recommendation (process, not a number call):** once item 1's shape questions are
resolved and any approved numeric changes land, re-run the sweep using each mission's
*specific* intended loadout from `GAME_DESIGN.md` §13's clear-rate table (Pulse Laser
Lv1 + starter modules for m1, Pulse Laser Lv2 + Generator Lv2 for m3, etc. — **not**
a flat clear-rate band; the table's floor declines per mission, m1≥85% down to m6≥45%,
with a shared >90% "too easy" ceiling) rather than the generic starter/mid/full tiers
`balance-sweep.ts` currently uses — that's the only way to get an apples-to-apples check
against the table that already encodes the intended pacing.

**Built 2026-07-10** (during the mission-tuning handoff — see the top-of-file note):
`tools/loadoutPresets.ts` gained `intendedLoadoutForMission(missionId)`, and both
`tools/simulate.ts --loadout intended` and `tools/balance-sweep.ts`'s `intended` loadout
row now resolve each mission's specific target gear and check its clear-rate against the
real per-mission floor/ceiling table (not the flat band this document originally, and
incorrectly, attributed to GAME_DESIGN.md §13 — that attribution was a factual error,
caught and corrected mid-session; see `balance-sweep.ts`'s `INTENDED_CLEAR_RATE_FLOOR`
constant for the real table). m1-m6 all now pass their real target under this check.

### Design decision requiring confirmation
- Whether to add per-mission "intended loadout" presets to the sweep tooling now (pure
  tooling, low risk, recommended) or defer until after item 1's balance questions are
  resolved (avoids running the more precise sweep twice). **Recommended: defer** — no
  point building the precise comparison until the mission shapes it's comparing against
  are settled.

## Item 3 — Recalibrate time-star thresholds (mechanical, not a balance call)

`GAME_DESIGN.md` §13 already documents the correct procedure: run 2000 clears per
mission and set T4/T3/T2/T1 from the 10th/25th/50th/75th percentile of completion time.
Today's sweep shows several thresholds are currently unreachable (0% or near-0% earn
rate): `m1-time-t4` (0.2%), `m2-time-t3`/`t4` (0%), `m3-time-t3`/`t4` (0%), `m4-time-t3`/
`t4` (0%), `m5-time-t3`/`t4` (0%), `m6-boss-260` (0.6%). That's 10 of the game's ~46 main-
mission stars currently unachievable by anyone — a real, present gap independent of the
bigger m5/m3 shape question.

**This is the one numeric item in this document that doesn't need Tomáš's per-number
sign-off on the resulting thresholds** — applying an already-approved formula to real
data is mechanical, not a creative balance decision. It still must happen *after* item
1's shape questions are resolved (if enemy counts/timing change, the percentiles change
too — do this last, not first, or the thresholds will need recalculating twice). It
**does** need one blanket go-ahead before anyone edits `missions.ts` for this reason —
see the checklist note below; the "no missions.ts changes without sign-off" guardrail is
about creative balance calls, and this item should be the one explicit, named exception
to it, not a silent violation of it.

**Tooling gap to close first — this doesn't exist yet.** `tools/simulate.ts` currently
only prints an aggregate average duration *over all runs, defeats included*
(`tools/simulate.ts:129-138`) — exactly the distortion item 2 already flags for
`avg-duration`. There is no existing output of per-run completion times, so the
percentile computation below can't be done from today's tooling as-is. Add a small,
approval-free (tooling-only) capability: emit each successful run's completion tick
(or write them to a file / stdout list) so the 10th/25th/50th/75th percentiles can be
computed from that list, excluding defeated runs entirely.

### Test plan — done 2026-07-10

- [x] Run it for every non-tutorial mission, using the mission's real intended loadout
  (`--loadout intended`, built as part of this pass — see item 2's update).
- [x] Compute the 10th/25th/50th/75th percentile completion time from that list — from

- [x] Update each mission's `missionStars(id, t1s, t2s, t3s, t4s)` call in `missions.ts`

- [x] Re-run `pnpm balance` and confirm 0 "UNREACHABLE" time-stars remain — confirmed at
  2000 runs/combo; hull/shield/all-kills stars improved as a side-effect of item 1's
  reshaping, not independently retuned.
- [x] `pnpm test` still green — 371 passing, no core logic changes, data-only.

## Item 4 — Testing approach: two layers, not one

The simulator (`pnpm sim`, `pnpm balance`) is authoritative for **clear-rate and star
achievability** — `GAME_DESIGN.md` §3 already states "the simulator is the truth" and
that principle doesn't change. But it is structurally blind to anything about how the
game *looks or feels*, because it never renders a frame. The side-weapon/HUD polish work
earlier this session is the proof: every bug found there (missing skip button hiding the
whole game field, a silently non-functional rear weapon, indistinguishable button states)
was found by **playing the game**, not by any simulator run, and none of them would ever
show up in a clear-rate number.

For mission-pacing work specifically, add a **manual playtest checklist** as a required
companion to the balance sweep — the sweep tells you *if* a mission is winnable, the
playtest tells you whether the winning *feels* like the intended tier:

### Manual playtest checklist (run after any mission/enemy change)
**Still open — needs Tomáš, not Claude.** m1/m3/m5 were reshaped this session (2026-07-10)
and pass the simulator's numbers, but nobody has played them yet. This is the one item
in this whole document that can't be closed by more simulation.
- [ ] Play the changed mission fresh, starter loadout, no prior knowledge advantage.
- [ ] Patient-tier missions (currently m1, m2, most of m3/m4): does the first 10–15
  seconds feel like a warm-up — enemies visibly drifting, time to react — or does
  something already feel urgent? (If urgent, it's probably not actually Patient-tier
  regardless of what the data says.)
- [ ] Escalating/Aggressive-tier missions (m5, m6, and wherever item 1's m3/m5 reshaping
  lands): does the escalation feel like a step change the player notices, or a
  continuous blur indistinguishable from the mission before it?
- [ ] Note anything that reads as "unfair" even if the simulator says the clear-rate is
  in-band — clear-rate is an average over strategies; a single human run can still feel
  bad for reasons that don't average out (e.g. an early bad-luck crit chain).
- [ ] Confirm HUD/audio feedback correctly reflects the new enemy mix (e.g. if item 1
  moves kamikaze earlier, does the collision-feedback burst added in the last polish
  pass fire correctly and look distinct from normal shield damage?).

### Design decision requiring confirmation
- Whether to add an automated "aggression" metric to `balance-sweep.ts` (e.g. average
  enemy time-to-impact per mission, or % of spawned enemies below a Patient-tier
  threshold), so the tier model in item 1 is numerically checkable in the report
  alongside clear-rate — not just eyeballed from `missions.ts`. **Recommended: yes, but
  as a follow-up after item 1's shape is settled**, not blocking this pass — it's new
  tooling scope (`tools/balance-sweep.ts` changes), and building a metric for a model
  that might still change shape is wasted work.

## Item 5 — Make the tooling "simulation-friendly," and a lean execution strategy

Two related but separate problems, both about *process* rather than balance numbers:

**Problem A — verifying a change today means eyeballing prose.** `pnpm balance` writes a
markdown report; a human or an agent has to read it to know if anything is out of band.
**Problem B — long sweeps shouldn't tie up an AI session just to wait.** A thorough sweep
(5000 runs/combo) takes ~20 minutes; an exhaustive one (50000 runs/combo) ~1 hour. An
agent turn held open for that whole duration spends session budget on pure idle waiting,
not reasoning — and then dumping the full report into context to re-derive "is anything
wrong" is wasteful when the tool could just say so directly.

### A. Make `balance-sweep.ts` report pass/fail itself — no eyeballing required

Today's thresholds are hardcoded inline — clear-rate flags at <60%/>95% and star flags
at <5%/>95% in `formatReport()` (`v2/tools/balance-sweep.ts:130,142`), with a third,
duplicate copy of the clear-rate flag in `main()`'s own quick-summary loop (`:195`) — and
`main()` never sets an exit code, so the process always exits 0 regardless of results;
nothing downstream can ask "did this pass?" without parsing prose. Also worth noting
while touching this file: the report's own header states the target band as **70–90%**,
but the code's actual flag thresholds are **60/95** — a real, if minor, inconsistency
(something can go unflagged at 65% clear even though the stated target starts at 70%).

Recommended (pure tooling, no balance numbers touched, no owner sign-off needed for the
mechanism — see the one exception below):
1. Extract the threshold numbers into named constants at the top of the file (fixes the
   magic-number smell and the 60-95-vs-70-90 mismatch — pick one number, use it in both
   the header text and the flag logic).
2. Add a `--json` output mode producing a compact
   `{ missionId, loadout, strategy, clearRate, flag }[]` structure alongside (or instead
   of) the markdown, so a script or agent can check results in a few lines instead of
   reading a report.
3. Set a non-zero exit code if any combo is flagged TOO_HARD / TOO_EASY / UNREACHABLE —
   turns "did anything break" into a one-line exit-code check; the full report only
   needs to be read when something *did* flag.

### B. Execution strategy: who runs simulations, and how, so it stays cheap

This is the direct answer to "make sure it doesn't eat AI-agent limits." The distinction
that matters isn't *which model* is running the session — it's **the main interactive
Claude Code session the user is already talking to, versus spinning up a separate agent
invocation (e.g. a Fable-model agent call) just to babysit a shell command.** Tomáš's
explicit preference: the mechanical work of running simulations happens in the ambient
session he's already in, not as a dedicated agent task. Concretely:

- Kick off any sweep longer than the quick default (500 runs/combo, ~2 min) using the
  Bash tool's `run_in_background` option, from the session already in use. The run
  proceeds on the machine without blocking that session; check back only when needed
  instead of waiting synchronously.
- After a run finishes, check the **exit code** first (once item A's non-zero-on-flag
  behavior exists). Only load the full report into context if the exit code flags a
  problem — once missions are tuned, most re-verification runs will simply pass, and
  that should cost near-zero tokens to confirm.
- Reserve dedicated agent invocations (Fable or otherwise) for what this whole document
  already uses them for: *reasoning* about design (aggression tiers, mission shape,
  which number to try next, reviewing a plan) — not for running or waiting on a command
  that the current session can already do directly with local Bash access. Spinning up a
  separate agent call just to hold a `pnpm balance` invocation open is spending a more
  constrained resource on a mechanical task for no benefit.
- For the exhaustive tier (~1 hour), don't run it inside an interactive session at all —
  background it and return later, or run it outside any AI session entirely (a plain
  terminal, or overnight) and hand the resulting `balance-report.md` to whichever session
  afterward as a static artifact. Interpreting a small markdown file is cheap regardless
  of how long it took to produce.

## Complexity analysis

No core simulation loops change in this document — everything proposed is either data
(`missions.ts`) or reporting-tool changes (`balance-sweep.ts`, `loadoutPresets.ts`). The
existing sweep is 36 combos × N runs; a *thorough* pass (5000 runs/combo, per the tool's
own usage comment) takes ~20 minutes, and an *exhaustive* pass (50000 runs/combo) ~1 hour
— know which one you're running before kicking it off, and per item 5, run anything
beyond the quick default in the background rather than holding a session open for it.
The proposed per-mission-specific-loadout sweep in item 2 would be *cheaper* than the
current generic sweep (6 missions × 1 loadout × 2 strategies = 12 combos vs. 36), not
more expensive.

## File hygiene

All proposed changes are confined to `v2/src/data/missions.ts` (balance data — owner-
approval gated, see the hard stop at the top), `v2/tools/balance-sweep.ts` and
`v2/tools/loadoutPresets.ts` (tooling, no approval gate beyond normal code review). No

a generated artifact (already gitignored or not — check before committing; if not
gitignored, don't commit a stale report).
